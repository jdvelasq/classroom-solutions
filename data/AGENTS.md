# AGENTS.md

## Scope

This repository contains complete solutions for the practical activities of the undergraduate course **Datos para Analítica**.

The repository structure and root-level infrastructure are already defined.

Do not redesign, reorganize, rename, move, delete, or create activity directories unless explicitly instructed.

Fill the existing activity skeletons in place.

Do not modify repository-level infrastructure such as `README.md`, `requirements.txt`, setup files, VS Code configuration, GitHub Actions, `.gitignore`, or other root-level configuration unless explicitly instructed.

The approved sequence and scope of activities are curriculum decisions. Do not merge, split, reorder, replace, or reinterpret activities unless explicitly instructed.

---

## Activity types

Activities may use the following prefixes:

* `PRE_`: in-class practical workshops developed incrementally with the instructor.
* `LAB_`: independent laboratory activities completed by students.

A `PRE_` is intended for guided development during class.

A `LAB_` is intended to verify that the student can transfer previously introduced concepts to a related but sufficiently different problem.

Do not convert a `PRE_` into a `LAB_`, or vice versa, unless explicitly instructed.

Do not assume that every `PRE_` requires a corresponding `LAB_`.

---

## Standard activity structure

Every activity follows exactly this structure:

```text
PRE_XX_activity_name/
├── data/
├── notebooks/
├── src/
├── submission/
├── temp/
├── tests/
│   ├── __init__.py
│   └── test_src.py
└── __init__.py
```

The same structure applies to `LAB_XX_activity_name/` when LAB activities are present.

This structure must always be preserved.

Do not remove unused directories.

Empty directories are preserved with `.gitkeep`.

Do not add extra top-level subdirectories inside an activity unless explicitly approved.

---

## Directory roles

* `data/`: input data required by the activity.
* `notebooks/`: notebooks containing the complete workshop solution when notebooks are appropriate.
* `src/`: Python source files, SQL files, reusable functions, pipeline components, interfaces, or other executable logic.
* `submission/`: final artifacts generated by executing the complete solution.
* `temp/`: temporary, intermediate, cached, staging, or disposable computational artifacts.
* `tests/`: pytest tests used for grading and validating the activity.

Input data belong in `data/`.

Generated intermediate data belong in `temp/`.

Final generated deliverables belong in `submission/`.

Do not manually place expected final outputs in `submission/` merely to satisfy tests.

## Pedagogical principle

Each activity represents a complete practical data-engineering case.

The solution must be suitable for incremental development during a live class when the activity is a `PRE_`.

Prefer a progression such as:

```text
data problem
↓
source or input data
↓
initial implementation
↓
limitation, failure, or engineering problem
↓
data-engineering principle
↓
improved implementation
↓
validation
↓
reproducible output
```

The problem is the organizing element.

Do not organize an activity primarily around demonstrating a package, library, framework, database engine, cloud service, or vendor technology.

A technology should appear because it helps solve the activity's engineering problem.

Prefer:

```text
problem
→ principle
→ implementation
→ validation
```

over:

```text
tool
→ features
→ tutorial
→ exercises
```

## Data for Analytics requirement

The purpose of the practical sequence is to develop the ability to make data reliably available for analytical use.

Depending on the activity, the solution may address one or more of the following capabilities:

* represent data appropriately;
* query and integrate data;
* transform data reproducibly;
* choose appropriate storage structures;
* ingest data from files, databases, or APIs;
* construct ETL or ELT pipelines;
* validate data quality;
* enforce schemas or data contracts;
* process incremental data safely;
* make pipelines idempotent;
* automate and orchestrate data workflows;
* process data at larger scale;
* process event streams;
* serve curated data to downstream analytical consumers;
* preserve metadata and lineage;
* enforce technical access, privacy, and governance requirements.

The activity should make the engineering purpose explicit.

Do not turn the course into a general database course, a software-engineering course, a cloud-certification course, or a collection of technology tutorials.

## Relationship with database fundamentals

Some students may have completed a previous database course and others may not.

Activities may therefore provide the minimum relational concepts required to proceed, including:

* tables;
* schemas;
* primary keys;
* foreign keys;
* relationships;
* referential integrity;
* basic normalization intuition;
* basic SQL.

Do not expand this level-setting into a full course on database theory.

Advanced formal treatment of normalization, database internals, transaction theory, or database administration is outside the normal scope unless explicitly required by an activity.

SQL should be developed primarily as a practical language for data integration, transformation, and preparation for analytics.

## SQL

When SQL is central to the learning objective, make the SQL logic visible.

Do not hide a SQL learning objective behind equivalent pandas or Python transformations.

Prefer readable SQL with explicit intermediate logic.

Use CTEs, views, derived tables, window functions, joins, aggregations, conditional expressions, casts, and related constructs when pedagogically justified.

Avoid unnecessarily clever or compressed SQL.

When appropriate, make the progression visible:

```text
source tables
→ integration
→ transformation
→ curated table or view
```

Queries should be deterministic whenever the underlying operation permits it.

When row order matters for grading or display, specify ordering explicitly.

## External APIs and unstable resources

Reproducibility takes precedence over dependence on a live external service.

When a live API is pedagogically useful, prefer one that is stable, public, and does not require private credentials.

* deterministic fixtures;
* small local HTTP services;
* previously captured datasets.

The activity may demonstrate how a real API is consumed while still preserving a deterministic offline path for testing and grading.

Do not make core grading depend on an unstable third-party service.

## ETL and ELT

When an activity implements a data pipeline, keep the stages conceptually visible.

When appropriate, use terminology such as:

```text

→ raw
→ staging
→ curated
→ serving
```

Do not create layers that have no pedagogical or engineering purpose.

Avoid unnecessary framework abstractions that hide the movement and transformation of the data.

## Pipeline reproducibility

A pipeline should produce predictable outputs from defined inputs.

Prefer explicit:

* input paths;
* output paths;
* schemas;
* transformations;
* parameters;
* dependencies;
* execution order.

Avoid hidden state.

Avoid reliance on accidental notebook execution history.

Avoid machine-specific paths.

Where appropriate, make a full pipeline executable from a single script, function, command, or clearly defined notebook sequence.

## Incremental processing

Activities involving incremental processing should distinguish clearly between:

* full refresh;
* append;
* incremental load;
* upsert or merge;
* changed records;
* checkpoints or watermarks when applicable.

The case should make clear why processing all historical data again is unnecessary or undesirable.

Incremental logic must be testable.

When appropriate, execute the pipeline multiple times to verify that previously processed data are handled correctly.

## Idempotency

When idempotency is part of the learning objective, demonstrate it explicitly.

Running the same operation twice with the same effective inputs should not unintentionally duplicate, corrupt, or otherwise change the logical result.

Tests should verify idempotent behavior when appropriate.

Do not claim idempotency merely because a script completes without raising an exception.

## Data quality

Treat data quality as an engineering property that can be validated automatically.

Depending on the case, checks may include:

* completeness;
* validity;
* uniqueness;
* consistency;
* freshness;
* referential integrity;
* accepted ranges;
* accepted categories;
* schema compatibility.

Quality rules should be explicit and testable.

Prefer automated validation over visual inspection.

When invalid data are intentionally introduced for pedagogical purposes, make the expected handling behavior explicit.

## Data contracts and schema evolution

When contracts or schema evolution are central to an activity, define the expected interface explicitly.

Prefer controlled failure, rejection, quarantine, or explicit adaptation over silently accepting incompatible data.

Do not hide schema violations through arbitrary coercion unless coercion itself is the intended lesson.

Design the course environment for heterogeneous student machines, not only the instructor's machine.

* macOS on Apple Silicon (`arm64`);
* macOS on Intel (`x86_64`);
* Windows (`x86_64`);

```text

+ portability
```

## Notebook formatting and output discipline

### First-cell problem statement

The first code cell of every workshop notebook must begin with a one-line problem description in the form:

```python
# Problema: <description>
```

The description must:

* be in Spanish;
* state the data-engineering problem rather than the solution technology;
* not exceed 240 characters including spaces;
* not name the implementation package or framework unless the technology itself is explicitly the subject of the problem;
* not reveal the final result.

Prefer:

```python
# Problema: integrar diariamente datos de ventas provenientes de varias fuentes y producir una tabla analítica reproducible.
```

over:

```python
# Problema: usar pandas y Airflow para hacer un ETL.
```

Leave exactly one blank line between the final initial comment line and the first executable statement.

---

### Cell readability

When a code cell begins with explanatory comments or section comments, leave exactly one blank line between the final comment line and the first executable statement.

Apply this spacing consistently.

Example:

```python
# VALIDACIÓN DEL ESQUEMA
# ---------------------------------------------------------------------
# La transformación solo debe continuar si la fuente conserva el contrato esperado.

validate_schema(raw_data)
```

---

### Comments

* Use concise comments to structure the live pedagogical progression.
* Do not create comment-only cells or use Markdown cells unless explicitly requested.
* Avoid excessive commentary that obscures executable logic.
* Section comments should explain the engineering concept, not merely restate the Python or SQL operation.
* Do not narrate obvious syntax.

---

### Displays and tables

Display intermediate data only when it helps explain the engineering reasoning.

Prefer concise samples, schema summaries, relevant columns, counts, validation results, or compact diagnostics over large raw tables.

Do not repeatedly display the same dataset after every transformation.

Avoid outputs that depend on terminal width, machine-specific configuration, or local absolute paths.

---

### Figures

Use figures only when they have a clear pedagogical purpose.

Possible purposes include:

* comparing execution behavior;
* showing data volume or partition distribution;
* showing pipeline structure;
* showing temporal event behavior;
* explaining quality or operational metrics.

Do not add decorative visualizations unrelated to the engineering objective.

When constructing a figure progressively across cells, do not display incomplete stages.

Display the final figure once when complete.

---

### Notebook output cleanliness

* Do not display machine-specific absolute paths.
* Prefer relative project paths.
* Remove temporary debugging output.
* Remove development-only variables or diagnostics from the completed activity.
* Remove redundant intermediate displays.
* Keep outputs concise enough for live classroom use.
* Do not expose credentials, tokens, environment secrets, or private configuration.

---

### Final execution

Before considering an activity complete, restart from a fresh kernel or clean execution state and execute all cells sequentially.

Confirm:

* no hidden-state dependencies;
* no execution errors;
* no machine-specific visible paths;
* no duplicated outputs;
* no development-only variables or diagnostics;
* no dependence on manually created temporary state;

## PRE Pedagogical Compactness Standard

Every `PRE` is a guided in-class activity.

Its purpose is to make one central data-engineering phenomenon directly observable during class.

A `PRE` must not become:

* a technology survey;
* a framework tutorial;
* a collection of independent mini-lessons;
* a compressed version of an entire professional topic.

### Central insight

Each `PRE` must have one primary engineering insight.

Supporting concepts are allowed only when they are necessary to expose that insight.

If several concepts can be removed without weakening the primary learning objective, remove them.

### Classroom code

Code must be:

* complete;
* visible;
* self-explanatory;
* deterministic;
* pedagogical.

A student reading the completed notebook later should understand **what the code does** without instructor explanation.

The instructor should spend classroom time explaining:

* why the operation is necessary;
* why the engineering decision matters;
* when the pattern is appropriate;
* what tradeoff it introduces.

Do not require the instructor to decode clever or compressed code.

### Notebook cell limits

Hard maximums:

| Weekly structure                        | Maximum cells per PRE |
| --------------------------------------- | --------------------: |
| 3 PRE in one week                       |                     6 |
| 2 PRE in one week                       |                     8 |
| Full-class PRE                          |                    14 |
| Final architecture PRE + course closure |                    10 |

These values are maximums, not targets.

Use fewer cells whenever the phenomenon remains clear.

### Code-line limit

Every code cell has a hard maximum of:

```text
12 effective code lines
```

Effective lines exclude:

* blank lines;
* comment-only lines.

Multiline SQL statements count as code lines.

Do not satisfy this limit by making code denser.

### Prohibited compression

Do not use unnecessary:

* one-line expressions;
* lambdas;
* method chaining;
* nested comprehensions;
* premature abstraction;
* classes;
* generic frameworks;
* clever Python;
* hidden side effects.

Readable multi-step code is preferred.

### Visible pedagogical logic

The central engineering logic must appear directly in the notebook before it is consolidated elsewhere.

The required progression is:

```text
show logic
↓
observe phenomenon
↓
understand behavior
↓
optionally consolidate in src/
```

Never use:

```text
helper()
framework.run()
engine.execute()
```

as a substitute for showing the mechanism being taught.

`src/` may consolidate code only after the notebook has made that logic explicit.

`src/` must never hide the central pedagogical implementation.

### Dataset size

Use:

> The smallest deterministic dataset that makes the target phenomenon unambiguous.

Do not enlarge datasets merely to make an activity appear realistic.

Scale is justified only when scale itself is the concept.

Students should normally be able to inspect the complete or nearly complete dataset used to introduce a phenomenon.

### Technology selection

Use the minimum technology necessary to expose the engineering concept.

Do not introduce a framework when removing it leaves the learning objective intact.

Prefer:

```text
transparent local implementation
```

over:

```text
realistic but opaque production framework
```

when the latter would hide the phenomenon.

### Observable phenomenon

Every `PRE` must contain an observable result that exposes the central idea.

Preferred patterns include:

```text
before → after
PASS → FAIL
duplicate → unique
full → incremental
attempt 1 fails → attempt 2 succeeds
OPEN → FINALIZED
upstream → downstream
local → partitioned
```

The phenomenon should be visible from the notebook outputs.

### Controlled failures

A `PRE` should normally contain no more than one controlled failure.

Two are justified only when they demonstrate meaningfully different behaviors.

Do not build catalogs of failure cases.

### Visible validation

The notebook should normally contain:

```text
1–2 central validations
```

only.

Visible validation exists to reinforce the learning objective.

Repository tests may be substantially more exhaustive.

The distinction is:

```text
notebook
→ teach

tests
→ guarantee
```

### Determinism

All classroom outputs must be deterministic unless nondeterminism itself is the explicit lesson.

Do not depend on:

* public APIs;
* current timestamps;
* random machine configuration;
* CPU count;
* unordered output;
* network availability;
* external services;

unless the specification explicitly requires and controls the behavior.

### Reproducibility

A completed PRE must execute from a clean generated state.

Do not rely on:

* previous notebook state;
* manually created files;
* machine-specific paths;
* hidden environment configuration;
* artifacts generated by another PRE.

Activities may be conceptually sequential but should remain technically executable independently unless explicitly specified otherwise.

### Failure semantics

Failures must represent the phenomenon accurately.

Examples:

```text
transient operational failure
→ bounded retry may be appropriate

deterministic data failure
→ retry does not repair the data
```

Do not introduce behavior merely because a production framework commonly supports it.

### Terminology

Use terminology consistently across PREs.

In particular:

```text
checkpoint / source high-water mark
→ batch incremental progress

watermark
→ event-time streaming progress
```

Do not use these terms interchangeably.

### Notebook versus production system

A PRE may simplify production behavior deliberately when that simplification makes the engineering principle visible.

When this occurs, state explicitly that the implementation is:

```text
a pedagogical model
```

and not:

```text
a production recommendation
```

### Final pedagogical test

Before a `PRE` may become `READY`, ask:

> Can a student read the completed notebook later and understand what every important operation does without the instructor?

and:

> During class, can the instructor spend most of the time explaining why the engineering decisions matter rather than explaining code syntax?

If either answer is no, simplify the PRE before implementation.

Pedagogical cell framing

Cuando una celda de código introduce una nueva decisión de ingeniería, abstracción, fallo controlado o validación, debe comenzar, cuando resulte útil, con uno o dos comentarios breves que indiquen el propósito de la operación.

Los comentarios deben redactarse en tercera persona impersonal.

Ejemplos adecuados:

# Se separan las entidades para evitar la repetición de sus atributos.

# Se verifica que todas las referencias correspondan a productos existentes.

# Se simula una falla transitoria para observar el comportamiento del reintento.

# Se compara el resultado reconstruido con los datos originales.

Se deben evitar comentarios que simplemente traduzcan la sintaxis:

# Se crea una variable.
# Se ejecuta un bucle.
# Se imprime el DataFrame.

El comentario debe explicar la intención del bloque, no describir línea por línea lo que hace el código.

Los comentarios exclusivamente pedagógicos no cuentan dentro del límite de 12 líneas efectivas de código por celda.
