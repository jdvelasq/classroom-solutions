# AGENTS.md

## Scope

This repository contains complete solutions for the practical activities of a graduate course on Prescriptive Analytics.

The repository structure and root-level infrastructure are already defined.

Do not redesign, reorganize, rename, move, delete, or create activity directories unless explicitly instructed.

Fill the existing activity skeletons in place.

Do not modify repository-level infrastructure such as `README.md`, `requirements.txt`, setup files, VS Code configuration, GitHub Actions, or `.gitignore` unless explicitly instructed.

## Standard activity structure

Every activity follows exactly this structure:

```text
PRE_XX_activity_name/
├── data/
├── notebooks/
├── src/
├── submission/
├── temp/
├── tests/
│   ├── __init__.py
│   └── test_src.py
└── __init__.py
```

This structure must always be preserved.

Do not remove unused directories.

Empty directories are preserved with `.gitkeep`.

## Directory roles

- `data/`: input data required by the activity.
- `notebooks/`: notebooks containing the complete workshop solution when notebooks are appropriate.
- `src/`: Python source files containing the complete solution when scripts, reusable functions, simulations, optimization logic, or interfaces are appropriate.
- `submission/`: final artifacts generated by executing the solution.
- `temp/`: temporary or intermediate files.
- `tests/`: pytest tests used for grading the activity.

## Activity solutions

Each activity represents a complete practical case.

The solution must be suitable for incremental development during a live class.

Prefer a progression such as:

```text
problem
↓
data
↓
initial analytical approach
↓
limitation or decision problem
↓
improved analytical reasoning
↓
prescriptive logic
↓
recommended decision
↓
generated output
```

Do not organize an activity primarily around demonstrating an algorithm, package, or library.

The real case and its decision problem are the organizing elements.

## Notebooks

Use notebooks when the analytical reasoning benefits from incremental development, experimentation, visualization, or interpretation.

Notebook code should:

- be concise and readable;
- proceed in a clear analytical sequence;
- use reasonably short code cells;
- expose intermediate results when they help explain the reasoning;
- avoid excessive Markdown;
- avoid long tutorial-style explanations;
- avoid unnecessary abstractions;
- remain suitable for live coding during class.

Comments should clarify analytical or computational reasoning when useful. Do not narrate obvious Python syntax.

An activity may contain one or several notebooks when this improves the analytical progression.

## Mathematical decision models in notebooks

Whenever an activity contains an explicit mathematical decision model, show its algebraic formulation in concise Python comments immediately before the code that implements or solves it.

Use readable AMPL-like notation rather than LaTeX, since notebooks use code cells only. Do not use Markdown cells for formulations or hide the model only inside Python calculations.

When applicable, explicitly identify sets or indices, parameters, derived quantities, decision variables, the objective function, and constraints. For example:

```python
# MODEL
# ---------------------------------------------------------------------
# Sets:
#   i in ITEMS
#
# Parameters:
#   value[i]
#   effort[i]
#   B
#
# Decision variable:
#   x[i] binary
#
# Objective:
#   maximize total_value:
#       sum{i in ITEMS} value[i] * x[i]
#
# Constraints:
#   subject to capacity:
#       sum{i in ITEMS} effort[i] * x[i] <= B
```

Keep the formulation pedagogical and proportional to the case complexity. Connect the decision problem to the subsequent Python implementation. Do not force a formal optimization formulation when the activity does not genuinely require one.

## Python source files

Use `src/` when the activity requires executable programs, reusable functions, simulations, optimization logic, models, interfaces, or other components better expressed as Python modules or scripts.

Keep source code:

- direct;
- readable;
- deterministic;
- easy to explain;
- minimally abstracted.

Do not introduce unnecessary classes, frameworks, architectural layers, factories, configuration systems, or helper modules.

Prefer the simplest implementation that clearly exposes the analytical reasoning.

## Data

Place only input data required by the activity in `data/`.

When a real-world case is too large or complex, reduce it pedagogically while preserving its essential decision structure.

The case must remain realistic enough for the central prescriptive decision to be meaningful.

## Temporary files

Place intermediate or disposable computational artifacts in `temp/`.

Do not place final activity outputs in `temp/`.

## Submission artifacts

`submission/` contains the final artifacts generated by executing the complete solution.

These artifacts must be generated by the analytical solution, not manually created merely to satisfy a test.

Depending on the case, they may include:

- CSV files;
- JSON files;
- trained models;
- figures;
- maps;
- HTML files;
- recommended allocations;
- schedules;

- policies;
- plans;
- other decision outputs.

For Prescriptive Analytics activities, the final artifacts should represent the resulting recommendation, decision, allocation, policy, plan, or other prescriptive output whenever appropriate.

## Tests

`tests/test_src.py` contains pytest grading tests.

Tests should verify observable results that matter for the activity.

Depending on the case, tests may verify:

- existence of required artifacts;
- expected file structure;
- required columns;
- valid data types;
- numerical values within tolerances;
- feasibility of a solution;
- capacity or resource constraints;
- nonnegative allocations;
- balance or conservation constraints;
- other essential properties of the prescribed decision.

Keep tests simple and robust.

Prefer testing outcomes and essential properties over irrelevant implementation details.

## Reproducibility

Solutions must be deterministic and reproducible whenever possible.

Use fixed random seeds whenever randomness is required.

Avoid unnecessary nondeterminism, hidden state, unstable external resources, or dependence on accidental execution order.

The same inputs and environment should produce the same grading artifacts.

## Dependencies

Use the packages already available in `requirements.txt`.

Do not add, remove, or modify dependencies without explicit approval.

Prefer the existing dependency stack whenever possible.

## Prescriptive Analytics requirement

An activity should not normally stop at:

- a prediction;
- a probability;
- a forecast;
- a simulation;
- a visualization;
- a descriptive metric.

These may be intermediate analytical inputs.

The solution should ultimately answer a decision question such as:

- what should be done;
- where resources should be allocated;
- how much should be allocated;
- when an action should occur;
- which alternatives should be selected;
- which entities should receive an intervention;
- which policy or plan should be followed.

Make the transition from analytics to action explicit.

## Notebook formatting and output discipline

### First-cell problem statement

The first code cell of every workshop notebook must begin with a one-line problem description in the form:

```python
# Problema: <description>
```

The description must be in Spanish, state the decision problem rather than the solution method, and not exceed 240 characters (including spaces). It must not name a computational method (PuLP, HiGHS, SciPy, scikit-learn, enumeration, MNL, or similar) and must not reveal the optimal answer. Leave exactly one blank line between the final initial comment line and the first executable statement, consistent with the cell-readability rule below.

### Cell readability

When a code cell begins with explanatory comments, section comments, or a mathematical formulation, leave exactly one blank line between the final comment line and the first executable Python statement. Apply this spacing consistently throughout all notebooks.

```python
# EXPECTED RECOVERY
# ---------------------------------------------------------------------
# Risk alone does not determine intervention value.

taxpayers["expected_recovery"] = (
    taxpayers["risk_probability"]
    * taxpayers["recoverable_amount"]
)
```

### Comments

- Use concise comments to structure the live pedagogical progression.
- Do not create comment-only cells or use Markdown cells.
- Avoid excessive commentary that obscures the executable logic.
- Section comments should explain the decision concept, not merely restate the Python operation.

### Figure construction and display

When constructing a figure progressively across cells, build it without displaying incomplete stages. Do not call `plt.show()`, `figure.show()`, `display(fig)`, or equivalent in intermediate cells, and prevent automatic inline display of unfinished figures.

Display the figure only once, after all intended panels, annotations, legends, and explanatory elements are complete. The final figure-building cell may use `display(fig)` or `plt.show()` as needed. Remove redundant display statements left over from development.

### Notebook output cleanliness

- Do not display machine-specific absolute paths; prefer relative project paths in visible output.
- Remove temporary debugging outputs and unused variables created only during notebook construction.
- Remove redundant intermediate displays from the completed activity.
- Prefer concise subsets, summaries, or relevant columns over large intermediate tables when they communicate the teaching point clearly.

### Figures

- Every figure should have a clear pedagogical purpose.
- Titles, axis labels, legends, annotations, and reference lines should make the decision interpretation understandable.
- Do not display partially constructed multi-panel figures.
- The final decision-product figure should appear once in its complete form.

### Final execution

Before considering an activity complete, restart from a fresh kernel and execute all cells sequentially. Confirm:

- no hidden-state dependencies or execution errors;
- no duplicated or prematurely displayed figures;
- no machine-specific visible paths;
- no development-only variables or outputs;
- deterministic reproduction of all submission artifacts.

## Optimization environment and solver conventions

Different activities may require different optimization technologies. Do not assume one solver or modeling package is appropriate for every Prescriptive Analytics problem.

### Default LP/MILP stack

The currently approved default stack for ordinary linear and mixed-integer linear programming is PuLP 3.3.0 for algebraic modeling, HiGHS through highspy 1.15.1 as the solver, and NumPy <2, with Python 3.9.6 as the execution baseline.

Currently approved LP/MILP requirements:

```text
pulp==3.3.0
highspy==1.15.1
numpy<2
```

When this stack is appropriate, select the solver explicitly:

```python
solver = pulp.HiGHS(msg=False)
model.solve(solver)
```

Do not rely on whichever solver happens to be installed or selected by default.

### Solver selection is problem-driven

PuLP + HiGHS is the default for ordinary LP/MILP activities, not a universal requirement. Propose another technology when the mathematical structure makes it clearly more appropriate, including specialized network optimization, nonlinear optimization, constraint programming, stochastic or scenario-based optimization, specialized scheduling, or other structures not naturally represented by the default stack.

Do not force a problem into PuLP + HiGHS for tool uniformity. Use: decision problem -> mathematical structure -> appropriate approved solver.

### Pedagogical optimization workflow

For small problems where exhaustive enumeration is computationally practical and pedagogically useful:

1. Show the algebraic decision model in AMPL-like Python comments.
2. Solve it by transparent exhaustive enumeration.
3. Solve the same model with the appropriate approved mathematical-programming solver.
4. Verify that both methods return the same optimal objective and decision.
5. Use enumeration to expose feasibility, alternative solutions, uniqueness, second-best solutions, and combinatorial growth.
6. Use the solver to demonstrate professional mathematical-programming practice and scalability.

Enumeration is a pedagogical device, not the expected method for realistically sized problems. For larger or structurally different problems, use the most appropriate approved solver directly when enumeration no longer adds instructional value.

### Reproducibility

Solver-based notebooks must be deterministic whenever the solver and problem permit it. Make solver choice explicit in code; results must not depend on which solver happens to be installed in the execution environment.

## Exhaustive search and mathematical-programming solution

For small explicit optimization problems where exhaustive search is practical and useful, preserve two complementary solutions to the same decision problem: transparent exhaustive search followed by a mathematical-programming model solved with an appropriate approved solver.

### 1. Exhaustive search

Enumerate first when the decision space is small enough. Show the candidate space, feasibility checks, how constraints eliminate candidates, objective evaluation, the best feasible solution, uniqueness, and second-best or nearby alternatives when useful. Make combinatorial growth visible.

Prefer `itertools.product`, `itertools.combinations`, direct loops, and simple deterministic filtering and evaluation. Do not hide the search logic behind unnecessary abstractions.

### 2. Mathematical decision model

After the exhaustive solution, show the formal model using AMPL-like Python comments immediately before the code that builds and solves it. Identify sets or indices, parameters, derived quantities, decision variables, objective, and constraints when applicable. Preserve the repository's requirement to introduce the algebraic model before its initial implementation; restate it here as needed to connect it directly to the solver implementation.

```python
# MODEL
# ---------------------------------------------------------------------
# Sets:
#   i in ITEMS
#
# Parameters:
#   value[i]
#   effort[i]
#   B
#
# Decision variable:
#   x[i] binary
#
# Objective:
#   maximize total_value:
#       sum{i in ITEMS} value[i] * x[i]
#
# Constraints:
#   subject to capacity:
#       sum{i in ITEMS} effort[i] * x[i] <= B

model = ...
```

### 3. Solver solution

Build the model explicitly and use the approved solver appropriate to its structure. Make the correspondence visible: algebraic model → Python model → solver → decision-variable values → recommended decision. The solver is not a black-box replacement for formulation.

### 4. Cross-validation

Verify agreement on the optimal objective, decision or selected set, and feasibility. If enumeration establishes uniqueness, confirm the solver returns that unique optimum. For multiple optima, check that any differing decisions are feasible and attain the same optimal objective.

```python
assert solver_objective == exhaustive_objective
assert solver_selection == exhaustive_selection
```

Use tolerance-aware comparisons for floating-point objectives when required; exact selection equality applies when verifying the same or unique optimum.

### 5. Scalability lesson

Use enumeration to illustrate computational growth:

```text
12 binary decisions -> 2^12 = 4,096 portfolios
20 binary decisions -> 2^20 = 1,048,576 portfolios
40 binary decisions -> 2^40 > 10^12 portfolios
```

Exhaustive search explains what optimization is doing; mathematical-programming solvers make the same class of decision problems scalable. Do not present enumeration as the preferred production method for realistically sized problems.

### 6. When not to enumerate

Use the mathematical model and appropriate approved solver directly when the search space is too large, enumeration would dominate class time without adding a concept, the structure is clearer through the model, or earlier activities have already established enumeration sufficiently. Justify the choice pedagogically rather than applying it mechanically.
